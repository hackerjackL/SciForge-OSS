# DAG Skill: Novelty Check & Idea Elimination

## Quick Reference

- **Purpose**: 4-axis evaluation (novelty×0.45 + feasibility×0.25 + relevance×0.15 + engineering grounding×0.15) → eliminate weak ideas
- **Input**: IDEA_DAG.json (from /idea-discovery)
- **Output**: novelty_report.json + survivor.md
- **Key**: at most 1 idea survives to the derivation phase; composite score < 0.6 → eliminated

## Use When

Use this skill after ideas have been generated by `/idea-discovery`. Each idea is independently evaluated for novelty, feasibility, and relevance. Weak or non-novel ideas are **eliminated** — only the strongest survives to the derivation phase.

This is the DAG's **filter/pruning gate**: it decides which branches survive and which die.

## Job

For each idea in the DAG, run a structured evaluation on 3 dimensions:

1. **Novelty** — has this idea been explored before? Is it truly original?
2. **Feasibility** — can this idea be executed with available tools and within the constraints?
3. **Relevance** — does this idea actually solve the original problem?

Based on the evaluation, each idea receives:
- **PASS** — proceeds to the next phase
- **FAIL** — eliminated immediately (reason recorded)
- **REVISE** — sent back to idea-discovery for refinement (max 2 rounds)
- **PENDING** — insufficient information; human judgment needed

Non-negotiable goal: **at most 1 idea survives to the derivation phase.** The DAG converges to a single path.

## 3-Dimension Evaluation Criteria

### Dimension 1: Novelty Check (v3.2 — frontier-aware, binary novelty → frontier advancement)

For each idea, check against existing literature (via `/universal-retrieval`). **v3.2 upgrade**: the old version only judged "done before or not" (binary novelty), which cannot support contribution positioning for a Q1 Intro — reviewers want "how much does it advance the current frontier", not "has anyone touched it". The new version has two layers:

1. **Binary novelty (existing, retained)** — search for prior work matching the idea's hypothesis and methodology; if a matching paper is found → check whether the idea provides clear differentiation. Score: 1-10 (1 = already done, 10 = fully novel).
   - ≥ 7 → `novel`; 4-6 → `partially_novel`; < 4 → `not_novel`
2. **Frontier advancement (v3.2 new, MANDATORY)** — produce `refine-logs/FRONTIER_GAP.md` containing all 3 items; missing any one → `WARN` (cannot enter the Phase 3→4 checkpoint):
   - **Frontier baseline**: explicitly list "the current SOTA / known strongest results / latest open problems in this sub-direction at the starting point of this research"; every item must attach at least 1 citation from the last 2 years (min_year=2020 onwards, but prefer the last 2 years). Never write "no research exists to our knowledge" — that is empty talk; be specific: "[Smith2024] reached X, [Lee2025] improved to Y, but Z remains unsolved".
   - **Delta claim**: state what this idea advances relative to the frontier baseline, in one sentence of increment ("we propose mechanism W, advancing Z from unsolvable to conditionally solvable / improving by Δ% on benchmark K"). The delta must be falsifiable — if delta is 0 or negative after the idea runs, the Phase 14 kill-argument will catch it.
   - **Why-not-before**: 3 reasons covering at least 2 of the 3 categories "technical constraints", "theoretical blind spots", "data availability". Prevents trivial novelty of the form "predecessors didn't do it because it is meaningless". If 3 reasons cannot be found, mark `why_not_before_weak` and deduct 2 from the novelty score.

**Frontier map (v3.2 new, gap-linked in v6.0)**: extract highly-cited papers from the last 2 years from `/universal-retrieval`'s `landscape_report.md` + `references.bib` to build a "frontier node graph" (each node = 1 paper from the last 2 years + its claims + open problems), written into `refine-logs/FRONTIER_MAP.json`. **v6.0 gap chain**: the graph's "unsolved nodes" are cross-linked to `literature/GAP_REPORT.md` gap-ids (every unsolved node that matches a GAP_REPORT entry carries that gap-id), and each idea's `gap_anchor` (from `refine-logs/GAP_ANCHOR_LOG.md`) must resolve: a cited gap-id that does not exist in GAP_REPORT.md → `gap_anchor_invalid` (FAIL); an idea landing on a frontier node linked to its anchored gap → frontier/novelty evidence recorded as `gap_consistent`. This idea must land on one of the "unsolved nodes" in this graph; landing on a "solved node" or a "blank meaningless region" → mark `not_novel` or `trivial_novel`. This graph is also directly consumed by `/paper-writing`'s Introduction section (the frontier-advancement triplet is exactly the Intro's contribution positioning).

**Binary + frontier composite novelty score**:
```
novelty_final = 0.5 × binary_novelty + 0.5 × frontier_advance
```
where `frontier_advance` ∈ [1,10]: clear frontier baseline + falsifiable delta + 3 why-not-before reasons = 10; missing frontier baseline = ≤4; unfalsifiable delta = -3; landing on a solved node = 1. The final novelty verdict now uses `novelty_final` (not the old `binary_novelty`).

**Why mandatory**: the first 3 paragraphs of a Q1 submission (Nature/PRL/IEEE T) Introduction must have frontier positioning + delta + why-not-before; if `/novelty-check` does not produce this triplet, `/paper-writing` can only rely on the agent fabricating on the fly — this is precisely the root cause of "AI-written Intros read as empty, with no concrete frontier anchoring". v3.2 moves frontier positioning forward into novelty-check, making the Intro's contribution section traceable to `FRONTIER_GAP.md`.

**Collision audit (v5.0 new mandatory step) — resolves the blind spot of "has anyone done this idea"**:

Observed in practice: ideas were generated without comparison against existing work, and the literature survey also missed checks — explicit per-paper collision checks are required. For each idea (using `/universal-retrieval`'s retrieval results — including the v6.0 **targeted waves** logged in `literature/TARGETED_WAVE_LOG.md`, which already carry a per-idea collision pre-check; supplement with further targeted retrieval if insufficient):

1. **Recall TOP-5 similar works**: search by "same problem domain + same method family", take the ≤5 most similar papers (must include work from the last 2 years; recall zero → the retrieval itself is suspect, mark `retrieval_suspect` and trigger re-retrieval)
2. **3-dimensional comparison matrix**: score each paper on 3 dimensions (0/1) — `same_problem` (same research question/RQ), `same_method` (same method family or differs only in components), `same_data` (same dataset/benchmark); write into the `collision_matrix` field of `novelty_report.json`
3. **Conflict resolution tree** (collision ≠ death sentence; handle by the strictest hit):

| Hit | Verdict | Handling |
|------|------|------|
| All 3 dimensions 1 (same problem + same method + same data) | `collision_fatal` | idea FAILs directly — this is reproduction, not research |
| problem+method both 1, data different | `collision_high` | default FAIL; downgrade to REVISE only if you can state **the scientific-question difference brought by the data difference** (not "run it on a different dataset") |
| problem 1, method different | `collision_medium` | REVISE — must spell out the **mechanism-level difference** from the nearest method (not hyperparameter differences), written into `differentiation.md` |
| only method similar, problem different | `collision_low` | PASS, but the Intro must cite and differentiate |

4. **Recency check**: if TOP-5 contains **no work from the last 2 years** while that direction is active (FRONTIER_MAP has a node in this domain) → mark `recency_gap`: either the retrieval is stale (re-retrieve), or this idea hit a cold region (deduct from the relevance score)
5. Persist `differentiation.md` and `collision_matrix` alongside `novelty_report.json`, for direct citation by `/paper-writing`'s Intro ("Unlike X, we ..." must be verifiable)

### Dimension 2: Feasibility Check

For each idea, evaluate:
1. **Tool availability** — are the required libraries/methods available?
2. **Time constraints** — can it be completed within the effort budget?
3. **Skill match** — do the available skills cover the methodology?
4. **Risk** — what can go wrong?

**Feasibility verdict:**
- All clear → `feasible`
- Some concerns → `risky`
- Major blockers → `infeasible`

### Dimension 3: Relevance Check

For each idea, verify:
1. Does it directly solve the original problem?
2. Does it respect the problem's constraints?
3. Is the output useful to the problem?

**Relevance verdict:**
- Direct match → `relevant`
- Partial match → `partially_relevant`
- Off-topic → `irrelevant`

## Combined Verdict Matrix

| Novelty | Feasibility | Relevance | Combined Verdict |
|--------|--------|--------|---------|
| novel | feasible | relevant | **PASS** ✅ |
| novel | risky | relevant | **REVISE** (fix feasibility) |
| partially_novel | feasible | relevant | **REVISE** (strengthen novelty) |
| not_novel | any | any | **FAIL** ❌ |
| any | infeasible | any | **FAIL** ❌ |
| any | any | irrelevant | **FAIL** ❌ |

## Composite Score

Survivor selection is based on the weighted composite score:

```
score = novelty × 0.45 + feasibility × 0.25 + relevance × 0.15 + engineering_grounding × 0.15
```

**Engineering Grounding normalization**: the EG score is taken from `engineering_grounding.eg_average` in `IDEA_DAG.json`, normalized to a 0-1 scale (divided by 10). If all EG sub-dimensions are N/A (pure humanities), EG = 1.0 (no penalty).

## Configuration

| Parameter | Type | Default | Description |
|------|------|------|------|
| `strictness` | enum | `normal` | `relaxed` (pass when uncertain), `normal`, `strict` (pass only when clearly novel) |
| `max_revise_cycles` | int | `2` | maximum times an idea can be sent back for revision |
| `min_survivors` | int | `1` | minimum number of ideas that must survive (0 = allow all eliminated) |
| `require_literature` | bool | `true` | whether to check literature to confirm prior work |

## Steps

### Step 1: Load Ideas from the DAG

Read `refine-logs/IDEA_DAG.json` — all ideas generated by `/idea-discovery` (aligned with idea-discovery's DAG path; OSS stores uniformly under `refine-logs/`).
Each idea has:
- `id` — unique identifier
- `title` — short description
- `hypothesis` — core claim
- `methodology` — how to derive/verify
- `perspective` — theoretical / computational / qualitative / interdisciplinary (aligned with OSS 4-perspective: theoretical / computational / qualitative / empirical; `empirical` perspective ideas proceed with `verification_type=computational`, aligned with idea-discovery)

### Step 2: Run the 4-Dimension Evaluation for Each Idea

For each idea, perform the 4-dimension evaluation per the criteria above (novelty + feasibility + relevance + engineering grounding EG).

> **R1 convergence note (v2.3)**: the 6-axis pre-screen (novelty/feasibility/relevance/tractability/data-readiness/EG) is already completed in `/idea-discovery`'s pre-screen — this skill **does not recompute these axes**; it only performs **survivor selection** over the ideas that passed the pre-screen and entered MCTS in `IDEA_DAG.json` (4-dimension composite score ranking + survival verdict). If an axis judged BLOCKED by idea-discovery still appears in the DAG, mark `inconsistent_pre-screen` and report it, rather than re-scoring in this step.

### Step 3: Compute Combined Verdicts

Use the verdict matrix to determine each idea's combined verdict.

### Step 4: Select the Survivor

If multiple ideas pass:
1. Rank by composite score (novelty × 0.45 + feasibility × 0.25 + relevance × 0.15 + engineering grounding × 0.15)
2. Select the highest-scoring idea
3. Record the eliminated ideas and their reasons
4. In `survivor.md`, **additionally attach** the Engineering Grounding tag (does not participate in ranking but human-visible)

If no idea passes:
1. Relax strictness by one level
2. Re-run the evaluation (max 1 relaxation)
3. If still no survivor → return `BLOCKED` (requires human intervention)

### Step 5: Write DAG State

```json
{
  "dag_id": "dag_20260719",
  "problem_id": "Q001",
  "status": "converged",
  "total_ideas": 3,
  "eliminated": [
    {"id": "idea_1", "reason": "not_novel: matching work found"},
    {"id": "idea_3", "reason": "infeasible: requires unavailable tool"}
  ],
  "survivor": {
    "id": "idea_2",
    "title": "A First-Principles Derivation...",
    "novelty_score": 8,
    "feasibility_score": 7,
    "relevance_score": 9,
    "engineering_grounding_score": 4.2,
    "eg_tier": "CONSTRAINED"
  },
  "next_skill": "theory-derivation"
}
```

## Output Artifacts

- `refine-logs/novelty_report.json` — full evaluation of all ideas (same directory as idea-discovery's DAG)
- `refine-logs/novelty_{idea_id}.md` — detailed evaluation per idea
- `refine-logs/survivor.md` — the selected idea
